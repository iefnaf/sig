# End-to-end spike

The full product loop in one Worker: Feishu webhook inbound -> steward M2 (a real LLM via pi-durable) or fixed-command dispatch (/派发, /状态) -> connector protocol (pairing, outbox, event inbox) -> M1 core (reducer, templates, outbound queue) -> replies and report cards back to Feishu. Deployed as `shepherd-hook` behind the custom domain `shepherd-spike.iefnaf.cc`.

- `src/index.ts`: Worker entry (Feishu webhook, /pair, /admin/*) and the Steward Durable Object combining the connector protocol from the do-protocol spike, the M1 core from ../steward-m1, and the M2 steward extension from ../steward-m2.
- `sim-connector.mjs <BASE> <pairingCode> [name]`: simulated connector; answers start_worker with a scripted event sequence. Pairing codes are single-use — a supervisor loop that fetches a fresh code per attempt is the practical way to keep one alive (deploys and network stalls kill the process).
- `connector.mjs --url <BASE> --repo <path> [--name <machine>] [--code <pairingCode>]`: the real connector (M2 scope of docs/design/connector-pi.md). Pairs once (token persisted in ~/.shepherd-spike/device.json, reused across restarts), one agent process per worker in its own git worktree (`shepherd/<workerId>` branch, from the thread's previous branch when relaying), the report extension + worker system prompt written to ~/.shepherd-spike/ext/, result adjudication per design §5.2, GitFacts merged into report events, progress throttled to tool-change/15s, unacked events resent on reconnect, idle process recycle after 10 min. Workers run `pi --mode rpc` by default, or Claude Code with `SHEPHERD_AGENT=claude` (`claude -p --output-format stream-json`, stream events normalized to pi's shapes, the report tool served over MCP with `--mcp-config` outside the worktree). Integration gotchas encoded in the adapter: `claude -p` reads its stdin prompt only up to EOF (write then `end()`), and MCP tool calls arrive namespaced (`mcp__shepherd__report`), not as the bare tool name. TODO vs the design: no auto-resume (a connector restart still loses in-flight runs — the DO's reap sweep and the startup orphan sweep now report them lost instead of leaving threads running forever), no send/interrupt from the chat UI (admin routes only), single repo per dispatch unless `--repo` is repeated (whitelist). The M3 reliability layer (2026-10-15, all verified live): stall watchdog (no stdout + ~0 CPU → one automatic respawn, second stall → `error:stall` question+card; both observed hangs idled under 1.5% CPU while quiet builds stay hot), uplink ping/downlink liveness (no frame for 90s → forced teardown+reconnect — it fired for real during a route outage and the system self-healed), DO-side conn sweep (silent sockets closed after 150s), timeout-failed commands requeued on hello with connector-side cmdId dedup (`cmdlog.json`) and persisted event seqs (`seqs.json` — the DO dedups on workerId+seq, so post-restart emits must not restart at 1), startup orphan sweep (leftover lock = live-at-crash → lost; clean worktrees removed), DO-side reapWorkers (running + offline 10min, or online-but-silent 45min → lost; fixed the stuck t_41aed061fb), and `/admin/send` + `/admin/interrupt` (follow_up / abort — both verified live against a running worker: a mid-run send changed the deliverable; an interrupt flipped the thread idle within seconds).

Bugs found and fixed while wiring this up (all worth remembering for the real implementation):

1. **Double-send race**: DO `onMessage` handlers interleave; two concurrent `flush()` calls can both deliver the same outbound row. Fixed with claim tokens (conditional UPDATE + ownership check).
2. **Missing schema migration**: `CREATE TABLE IF NOT EXISTS` does not add columns to existing DO tables; deploys against live storage need idempotent `ALTER TABLE` migrations.
3. **No fetch timeout + no retry driver**: a hung Feishu send blocked the events handler forever (acks stopped, nothing retried). Fixed with 10 s timeouts and an alarm-driven `retryOutbound`.
4. **Dispatch picked a dead device** (first row in the device table) whenever the online lookup came up empty — an isolate swap can silently drop the connector socket with no close frame, so `getWebSockets` correctly returns nothing and the old code fell through to a random dead device. Fixed: a thread keeps the machine its last worker ran on (queued, resumed on reconnect); a new thread with nothing online refuses with a note.
5. **Queued commands never retried**: `deliver()` only ran at dispatch and at hello; if the device was offline at dispatch the row sat queued forever. `resendUnacked` now sweeps queued rows, delivers when the device returns, and fails them after ~30 idle minutes.
6. **Secret rotation needs a new isolate**: a resident Durable Object keeps the env it was constructed with, so a rotated DEEPSEEK_API_KEY kept producing `model_error` until eviction/redeploy. Same for code: a resident DO (kept alive by an open WebSocket or alarms) serves the previous version for minutes after `wrangler deploy` returns — close the sockets and let it idle out before judging a deploy.
7. **pi-ai provider construction in Workers**: env-var auth reads the wrong context; build the provider with `createProvider` and an inline `auth.apiKey.resolve`. `PiModel` is `{provider, id}` (not `modelId`); the lazy OpenAI-completions API import comes from `api/openai-completions.lazy`.
8. **pi RPC responses use `success`, not `ok`**: checking `r.ok` on a `{success: true}` response made the connector report `prompt rejected` while pi happily did the work. Always check `r.success === false || r.error`.
9. **The one-dispatch guard leaked across runs**: the extension instance outlives runs in the DO, so a `dispatchedThread` set by message N silently blocked a different target on message N+1 (the model then told the user "防重复机制拦了两次" — honest, but wrong). The guard now resets when the run's provenance changes.
10. **Downlink can die silently too** (the mirror of bug 4): the DO sees the connector socket as ready and `send()` raises nothing, but the connector receives no bytes; the command ack-times-out through 4 attempts, ends `failed`, and hello-redelivery only picks `queued`/`sent` — so the dispatch is permanently lost while both ends look healthy. A connector restart (fresh socket) plus a re-sent message recovers. Real fix: ws ping/pong heartbeat on both sides, redeliver `failed` on hello with connector-side cmdId dedup, or a periodic command resync.
11. **Routing decides whether relay ever triggers**: 「按 greeting 方案实施」 produced a *new* thread, so the thread-scoped `base` lookup found nothing and leg-2 started from HEAD (duplicate work, no handoff). Phrasing that names the thread (「回到 greeting 调研那条线程继续」) attached correctly and relayed. deepseek-flash judgment. Fixed after the fact: the steward ROLE_PROMPT now carries an explicit continuation rule (「按 X 方案实施 / 接着 X 继续 / 在 X 基础上做」 with X a thread's output → attach that thread), guarded by eval dataset section G (`../steward-m2/eval/dataset.ts`, 6 relay cases incl. an external-doc contrast — 6/6 pass, 100/106 overall, commit 1337602).

Setup: secrets SERVER_KEY, ADMIN_TOKEN, FEISHU_APP_ID, FEISHU_APP_SECRET, FEISHU_OWNER_OPEN_ID, DEEPSEEK_API_KEY; custom domain attached in the dashboard; Feishu app webhook pointed at https://<domain>/feishu (see docs/research/feishu-channel.md §8.2 for the console-republish requirement). Diagnostics: `/agents/steward/owner/__diag` (plain HTTP, bypasses the RPC envelope) shows constructor state, live connections, devices, and recent outbox rows; `/admin/stats` summarizes runs/threads/commands.
