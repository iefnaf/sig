# ADR-0005: Web entry and local worker sessions

The browser authentication entry is superseded by [ADR-0010](0010-browser-password-authentication.md). Session viewing and local transcript ownership remain unchanged.

Status: accepted and implemented (2026-10-18; renumbered when ADR-0002/0003 took the Sig brand and the owner API). Decision 2 (Cloudflare Access front door) was superseded twice — first by the device-first claim (ADR-0006, then rejected), finally by ADR-0003: the session is opened by a one-time link minted through the SERVER_KEY-gated owner API. Decision 8 (keep the Feishu code, unreachable) is superseded by ADR-0003's deletion of the channel. Its "direct worker chat stays deferred" line (Consequences) is narrowed by [ADR-0011](0011-direct-worker-chat-from-session-view.md) (implemented): a session view may act on the worker it already shows. Amends ADR-0001 decisions 4, 7–9 and 12, and ADR-0004's channel and onboarding decisions. How it is built is in [design/web-entry.md](../design/web-entry.md).

The owner wants to use the web workspace as the sole user entry for now and retire any chat-platform dependence. The first session viewer covers sessions started by Pip; the owner does not need to read full sessions while their machines are offline. Keeping original session records on the machine preserves the existing data boundary and avoids a cloud transcript archive.

## Decisions

1. **Use the workspace for the whole owner workflow.** Login, initial configuration, machine pairing, conversation, reports and decisions work in the browser. Owner identity belongs to the deployment independently of any messaging account: whoever holds SERVER_KEY (ADR-0003), with the browser signing in through a one-time login link minted by `POST /api/login-link`.
2. ~~**Authenticate the owner with Cloudflare Access, and verify it in the Worker.**~~ (superseded — see the status note.) An Access application fronts `/app*` and allows the owner's address; the Worker checks Access's signed token on every request — pages, API calls and the browser WebSocket — for signature, issuer, audience, expiry and an email exactly equal to `OWNER_EMAIL`, and answers `401` itself otherwise. The Worker is the enforcement point, so a hostname Access does not cover (`workers.dev` included) is not a way in. The workspace stays closed until `OWNER_EMAIL`, `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` are set. *Rejected:* a Worker-level Access policy (Cloudflare documents that it does not support WebSockets, which both the browser and the connectors use), and an application-level login of our own (a second credential system to own for one person).
3. **Give machines their own doors.** `/pair` (one-time code, rate-limited) and the machine socket `/agents/steward/owner` (per-machine device credential) stay outside Access, which cannot answer a headless connector's login; nothing about how a connector reaches the steward changes. A device credential never authorizes an owner request and an Access token never authorizes a machine.
4. **Browse Sig's worker sessions inside the workspace.** Each Thread exposes its current and previous worker sessions in the same application, replacing the separate raw-process page. The scope excludes discovering or importing sessions started independently in a terminal; changes made locally to an existing Pip session remain part of that session.
5. **Keep original session records on their machine.** An authenticated owner requests content through the connector and cloud relay. The relay does not persist or log raw transcript content or attachments. Existing cloud records of owner/Pip conversation, Thread summaries, worker reports and decisions remain available independently.
6. **Require the connector to be online for session reads.** A finished agent process does not prevent reading its session file. A disconnected machine makes further history reads unavailable; the workspace shows that state and can retry after reconnect. There is no cloud archive or persistent browser cache to make full sessions available offline.
7. **Make session detail inspectable, and lose none of it.** The viewer shows every recorded entry — messages, tool calls with arguments and results, bash executions, images, compaction and branch notes — and a record this version does not recognise is shown raw, not dropped. The connector sends each entry as bounded fragments of its own JSON, resumable from an opaque cursor, so size limits bound a page, never an entry. Adapter limitations and missing local records are explicit.
8. ~~**Keep the Feishu code, unreachable.**~~ (superseded by ADR-0003: the channel code was deleted; it lives in git history.) The channel's code stays in the repository behind a test-only fixture (the pre-Access Worker entry), not exported by the production entry: no webhook, no login links, no setup page, no Feishu delivery. *Why:* the steward's dispatch, notification and card logic is interleaved with it and the suites that guard that logic are Feishu-shaped; deleting it is a refactor with real regression risk and nothing to gain for this change. It can be removed, or revived as a channel, later without touching the workspace.

## Consequences

- Reports and pending decisions are recorded in the workspace even when no browser is connected. Removing Feishu also removes closed-page push delivery; browser push is a separate future capability, not a prerequisite.
- Existing deployments migrate in place: threads, workers, pending decisions and messages still queued for Feishu appear in the workspace; the Feishu owner id is kept as the owner's internal id so old rows stay consistent. The one thing an upgrade requires is setting the three Access values.
- The application session (CSRF carrier, logout) is bound to the Access subject and lasts seven days, but it authorizes nothing by itself: every request still needs a current Access token. When the token runs out the page reloads itself (or, with an unsent message, asks the owner to) and open sockets are closed lazily; nothing is sent to an expired session.
- Viewing a session's recorded history (decisions 4–7 above) remains read-only. Mechanical control of the worker it shows — send/interrupt/resume/stop — is no longer deferred; see [ADR-0011](0011-direct-worker-chat-from-session-view.md). Anything needing Sig's judgment still goes through Pip/Sig conversation.
- A local session file that is deleted cannot be recovered from the cloud. An offline or missing-history state never appears as an empty successful conversation.
- **Known limits.** A session is read forward from its start, so a very long one finishes loading before anything is shown (then the page draws the last 200 entries, earlier ones are one click away, and loading pauses at 64 MB per allowance with a "Load more"); a tail-first read would need a backward cursor. Branch marking applies to pi only — Claude Code's parallel tool results look like forks and are not. The text the system itself generates (cards, timeline lines) is still Chinese, as in ADR-0002.
