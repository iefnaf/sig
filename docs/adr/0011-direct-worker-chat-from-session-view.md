# ADR-0011: Direct worker chat from an open session view

Status: accepted (2026-10-24). Amends ADR-0004's "Phase one omits memory management, routine management and direct worker chat" and ADR-0005 decision "Viewing a session remains read-only. Direct worker chat stays deferred under ADR-0002; instructions and interventions continue through Pip." Narrows ADR-0001 decision 7 ("intervention goes through conversation") for the single case covered here: a session the owner already has open. Implemented against [connector-do-protocol.md](../design/connector-do-protocol.md) §5.3/§6.8 (issue #84).

Context: the workspace's "one conversation" model (ADR-0004 decision 1) routes every owner instruction through Sig because, in general, Sig has to resolve which Thread and which worker an instruction targets, and may enrich it with memory before dispatch. That resolution step is needed when the owner is typing into the single conversation. It is not needed when the owner has already opened a specific worker session's view — the UI itself has picked the `workerId`, so forcing a round trip through Sig's reasoning to re-derive a target that's already known adds latency and an extra hop for no benefit, especially from a phone where the owner wants quick, mechanical control (stop, interrupt, a short steering note) over a session they're already watching.

## Decisions

1. **A browser connection that has declared which session it is viewing may send mechanical commands directly to that worker.** New messages `subscribe{workerId}` / `unsubscribe{}` mark the open session view, and `worker_cmd{id, workerId, kind, args}` (§6.8) dispatches to it. **v1 scope is `kind ∈ {send, interrupt}`** — the two that already have a deterministic, LLM-free dispatch path (`Dispatcher.sendToWorker`/`interruptWorker`). `resume` and `stop_process` have no such path yet (`resume` is folded into `continueThread`'s internal logic; `stop_process` is not exposed as a steward action at all) and are left for a follow-up once one exists to reuse — this ADR does not invent a second, parallel implementation of them. The DO calls the same `Dispatcher` methods the steward's tools call, with no steward/LLM step in between; the connector-side wire format is identical to a steward-issued `cmd`, so the connector needs no change.
2. **Targeting is server-verified, not client-asserted.** The DO accepts `worker_cmd` only on a connection that has sent `subscribe{workerId}` for that exact `workerId` (tracked on the connection's own state, cleared on `unsubscribe` or disconnect — not client-asserted per-message). A mismatched or missing subscription gets `error{code:"forbidden"}`. This is what keeps "the UI already disambiguated the target" a server-enforced property, not just a UX convention.
3. **Idempotency reuses the existing web mutation pattern.** The `worker_cmd`'s `id` is the caller's `sh_web_request` value (ADR-0004 decision 3) and becomes the command's `cmdId` directly — a retry is one effect, same guarantee the rest of the owner API already gives. This is the one place `cmdId` is not steward-tool-call-derived (§7.1); the outbox schema does not change, it just gets a second source of ids.
4. **Sig is told asynchronously, not asked synchronously.** `Dispatcher.sendToWorker`/`interruptWorker` already write a Thread timeline entry as part of the normal dispatch (unchanged by this ADR) — tagging the `provenance` as `web_direct` is enough for Sig to tell, next time it reasons about that Thread, that this one didn't come from its own tool call. Sig is not woken for it. Sig still learns the outcome the normal way: the worker's resulting events (`progress`/`report`/`settled`) flow back through the existing event pipeline (§4.3) and wake Sig under the existing rules (§8 item 2) regardless of who issued the command that produced them.
5. **What stays mediated.** Anything that needs Sig's judgment — "which machine," "does this fit what we're already doing," enriching a free-text instruction with memory before it reaches the worker — still goes through the one conversation. This ADR only removes the mediation step for the case where the owner has already picked the target by opening its view; it does not add a second place to address Sig, and it does not change `web`'s inability to call `register_repo`, `start_worker`, or anything else requiring project/account-level trust.

## Consequences

- `start_worker` and `register_repo` remain steward/owner-web-page actions, not session-view actions — a session view only talks to the worker it already shows, it cannot start a new one.
- A `send` issued this way skips whatever enrichment Sig would otherwise add (relevant memory, Thread context). That is the intended trade-off for "微操": the owner is typing straight to the agent they're watching, not asking Sig to relay.
- `interrupt` dispatched this way no longer needs to be "asked of Pip in conversation" (ADR-0001 decision 7, reaffirmed by ADR-0004's phase-one note) — it is mechanical and the protocol already carries it with no LLM judgment involved in forwarding. `stop_process` and `resume` stay exactly as deferred as before, tracked as follow-up work rather than silently promised by this ADR.
- The security property degrades gracefully if subscription state is ever lost (DO restart, reconnect race, hibernation): the connection simply loses the ability to send `worker_cmd` until it re-subscribes, rather than silently targeting the wrong worker.
- `cmd_ack`/`cmd_result` for a web-direct command are relayed back to the subscribed browser (§6.8) so the session view can show real delivery/outcome state, not a fabricated optimistic one.
