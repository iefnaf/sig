# Deploying Shepherd

A Shepherd deployment lives entirely in **your own Cloudflare account**: one Worker (the steward, with its Durable Object), no third-party service in the middle. Around it you connect a Feishu bot and, on each of your machines, a connector process. This guide walks the whole path: deploy → open the setup page → Feishu → connector, then everything operational (custom domains, model keys, costs, secret rotation, updates).

Spec: §12.1 (onboarding), §12.3 (cost transparency). Decisions: [ADR-0001](adr/0001-mvp-implementation-baseline.md) #8, #10, #11.

## One-click deploy

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/iefnaf/shepherd)

The button clones the repository into your own GitHub account, provisions the Durable Object, and deploys through Workers Builds. Later pushes to your copy's `main` branch redeploy automatically.

The deploy form asks for four things:

| Field | What to enter |
| --- | --- |
| Worker name | Anything; it becomes `<name>.<your-subdomain>.workers.dev`. The default `shepherd-steward` is fine. |
| `SERVER_KEY` | A random secret that signs connector device tokens and encrypts your Feishu credentials. Run `openssl rand -hex 32` and paste the output. Keep a copy somewhere safe. |
| `SETUP_TOKEN` | A one-time password that unlocks the setup page. Run `openssl rand -hex 32` **again** (a different value) and paste it. |
| `MODEL_KEY` | Your model provider's API key — [DeepSeek](https://platform.deepseek.com) by default. You can leave it empty for now and set it later (see [Model provider](#model-provider)). |

Both random secrets are generated by you, in the deploy flow itself — nothing sensitive ever passes through this repository or its maintainers. They land as encrypted Worker secrets in your account.

> **Terminal person?** Manual deploy works the same:
> ```sh
> git clone https://github.com/<you>/shepherd && cd shepherd
> pnpm install
> wrangler deploy                 # uses the wrangler.jsonc at the repo root
> wrangler secret put SERVER_KEY  # openssl rand -hex 32
> wrangler secret put SETUP_TOKEN # a second, different openssl rand -hex 32
> wrangler secret put MODEL_KEY   # optional for now
> ```
> (Secrets come after `deploy` because the Worker has to exist first; each `secret put` immediately redeploys a new version.)

### After the deploy: the setup page

Open:

```
https://<worker-name>.<your-subdomain>.workers.dev/setup?token=<SETUP_TOKEN>
```

The page starts with a **self-check**: it is rendered by your Durable Object, so the fact that it loads at all proves the Worker, the DO, and its storage are alive. It also classifies the host you opened it on — `*.workers.dev` vs a custom domain — and warns when Feishu webhook delivery cannot work from there (see the next section).

Then follow the on-screen steps: scan the QR code with Feishu to create the bot (the scanner becomes the owner), scan once more to add the switch permission, switch event delivery to the webhook, republish the app in the console, and DM the bot — that first DM proves delivery switched and closes the setup page permanently. Manual credential entry stays available as the fallback at every step. Details: [Feishu setup](#feishu-setup).

## Custom domain

**Every deployment needs one.** Two independent reasons, both verified live ([Feishu research](research/feishu-channel.md) §3, §8.2):

1. **Feishu webhook delivery — affects everyone.** Feishu's event servers sit in mainland China and cannot reach `*.workers.dev` (DNS pollution + TLS resets on the SNI). PATCHing a workers.dev URL as the event destination fails Feishu's own URL verification with error 210042 — live-tested. Without a custom domain, the webhook switch on the setup page cannot succeed, so no Feishu event ever arrives.
2. **Your own access — affects mainland users.** In mainland China, `workers.dev` is blocked for people too: the setup page, report links, and web pages don't open without a proxy, and the connector's WebSocket to the steward connects to the same blocked hostname.

To bind one:

1. Have a domain whose DNS is hosted on Cloudflare (free plan is enough).
2. Dashboard → **Workers & Pages** → your shepherd Worker → **Settings → Domains & Routes** → **Add → Custom domain**, e.g. `shepherd.example.com`. Cloudflare creates the DNS record and the certificate.
3. Reopen the setup page on the new domain — `https://shepherd.example.com/setup?token=<SETUP_TOKEN>` — the token is unchanged, and the self-check card turns green. The webhook URL the setup page offers now uses the custom domain too.

You don't need the domain before starting: the two QR scans and the manual-credential flow all work from `workers.dev` (only Feishu's *inbound* delivery is blocked). Bind the domain any time before the webhook switch and reopen the page — the flow picks up the new origin automatically.

Caveats, honestly stated:

- **Mainland reachability of a Cloudflare custom domain is common but not guaranteed** — the spike's own domain returned 200 from mainland China with no proxy (~1.2 s, [research §8.1](research/feishu-channel.md)); reachability still varies by domain, region, and ISP. The *definitive* test is Feishu's own URL validation during the webhook switch on the setup page — if that step succeeds, delivery works. If it fails, try a different domain (or front one with a CDN you control) and run the switch again.
- Do it before the webhook switch, not after: the switch step is what proves the domain works.

## Model provider

The steward's own conversation model is **provider-configurable, default DeepSeek** (`deepseek-flash`, the routing-eval baseline — ADR-0001 #11). The `MODEL_KEY` you set at deploy (or later with `wrangler secret put MODEL_KEY`, or in the dashboard under Settings → Variables → Secrets) is stored encrypted inside your own Cloudflare account and is used only for outbound calls from your Worker to the provider — it never passes through any third party, including this project's maintainers (spec §12.2).

DeepSeek is the default partly because it is cheap and reachable; any OpenAI-compatible provider works once provider config lands in the steward conversation milestone. Changing the model later means re-running the routing eval (ADR-0001 #14) — a configuration for careful users, not a form field.

Note the boundary: `MODEL_KEY` pays for the **steward's own** thinking (routing, replies, summaries). The coding agents the steward dispatches on your machines (pi, Claude Code) use **their own logins/keys on those machines** and are never billed through this deployment.

## Feishu setup

The setup page walks the whole thing; this is the map so you know where you are:

1. **Scan #1 — create the bot.** A QR code starts Feishu's official device flow; the app is created with bot capability and default permissions, and **the scanner is bound as the owner**. The prefilled name starts with your deployment's host label so multiple deployments are distinguishable.
2. **Scan #2 — add the switch permission.** A second QR adds `application:application:patch` (the credential set is not rotated by this).
3. **Switch to webhook.** The steward PATCHes the app's event configuration to `https://<your-domain>/channels/feishu/events` — events `im.message.receive_v1` (messages) and callback `card.action.trigger` (report-card buttons). Feishu validates the URL during the save — this is the reachability moment of truth.
4. **Republish in the console.** Open the developer console → 版本管理与发布 → create a version and publish. The API cannot replace this step: without a republish, events keep flowing to the long connection and nothing arrives.
5. **DM the bot.** The first direct message that arrives over the webhook proves delivery switched; it also closes the setup page permanently.

If you prefer (or the QR flow fails), the manual fallback is always available on the same page: create an enterprise app yourself, paste its App ID / App Secret / Verification Token (validated live against Feishu), configure the event subscription by hand, publish, DM. Lark (international) accounts work too — the flow switches domains automatically.

## Connector install

Each machine you want to dispatch work to runs a small daemon that holds a WebSocket to the steward and drives the local coding agents.

- **The easy way** — the distribution milestone's npm package ([#26](https://github.com/iefnaf/shepherd/issues/26); not yet published):

  ```sh
  npx @iefnaf/shepherd connect https://shepherd.example.com <pairing-code>
  ```

  The pairing code is issued in the Feishu conversation once you are the bound owner (the chat command that mints it ships with the machine-management milestone, [#22](https://github.com/iefnaf/shepherd/issues/22)). `connect` installs a launchd agent (macOS) or systemd user unit (Linux) so the connector survives reboots; `shepherd status / logs / stop / uninstall` manage it.

- **From source** (works today, before the package ships):

  ```sh
  git clone https://github.com/<you>/shepherd && cd shepherd
  pnpm install
  npx tsx apps/connector/src/cli.ts connect https://shepherd.example.com <pairing-code>
  ```

  Until the chat command lands, the deployment owner mints the pairing code over the Durable Object's `createPairing` RPC (e.g. from the Workers dashboard console or a one-off script against the `Steward` binding).

Prerequisites on the machine: Node ≥ 22.18, and the coding agent you intend to use (pi first, Claude Code next) already installed and logged in — Shepherd never touches the agent's own credentials.

Then allow-list the repositories the steward may work in (this is deliberately machine-local and cannot be edited remotely):

```sh
shepherd add-repo ~/code/myproject     # or: npx tsx apps/connector/src/cli.ts add-repo ~/code/myproject
```

## Costs

Shepherd is designed to be **dormant — and cost nothing — most of the time** (spec §12.3). Orders of magnitude, so the bill never surprises you (check current prices on Cloudflare's pricing page; these drift):

**Cloudflare (the deployment itself)**

- The meters that matter: **Durable Object requests** (every inbound Feishu event and every WebSocket message to/from the connector counts as one), **DO duration** (billed in GB-seconds while the steward is *awake* — a hibernating steward with an idle WebSocket bills nothing), and **SQLite storage** (your ledger/threads; kilobytes to megabytes).
- **Free tier**: a personal deployment — a connected machine, a handful of conversations a day, the daily digest — generally fits inside the Workers free plan. $0.
- **Workers Paid ($5/month)**: covers a comfortably heavy personal deployment; beyond the included allowances the overage meters are fractions of a cent per million requests and ~$0.20/GB-month of storage. Realistic total for one active user: **$0–6/month**. If you are paying tens of dollars, something (a hot loop, a chatty routine) is misbehaving — the DO's logs will show it.

**Model calls (the steward's own LLM)**

- The drivers: **number of conversations/messages** (each inbound event can wake the model), **summary and digest generation** (routines), and report composition (mostly templates — no LLM). Sending a task to a coding agent costs *one* steward wake plus the agent's own tokens on your machine.
- With the default DeepSeek-class model, a wake over a conversation's context is a few thousand tokens — **well under a cent each**; a moderately active day is **single-digit cents**; a heavy month is **a few dollars**. Past the daily budget soft cap the model stops waking entirely (ADR-0001 #15).

**Feishu**: the custom-app bot this uses is free.

## Secrets and rotation

| Secret | Role | Rotating it |
| --- | --- | --- |
| `SERVER_KEY` | Signs connector device tokens; encrypts (seals) the Feishu credentials in DO storage. | `wrangler secret put SERVER_KEY`. **Blast radius:** every connector token becomes invalid (machines must re-pair with new codes) and the sealed Feishu credentials become unreadable — by design the setup page reopens so you can re-enter or re-scan them. Do it when a machine is lost or a token may have leaked. |
| `SETUP_TOKEN` | One-time gate for the setup page. | `wrangler secret put SETUP_TOKEN`. Only meaningful before onboarding completes; once the owner is bound the page is closed permanently regardless of the token. |
| `MODEL_KEY` | Your model provider key. | `wrangler secret put MODEL_KEY` whenever the provider key changes. No other effect. |

### Evict the resident isolate before verifying a rotation

> A Durable Object isolate that something keeps alive — an open connector WebSocket, a pending alarm — **pins the previous code and the previous secrets for minutes after `wrangler deploy` (or `secret put`, which deploys immediately) returns.** This was verified live in the spike phase ([spike conclusions](spike-conclusions.md) §2). Testing a fresh secret against such a resident isolate either proves nothing or makes a healthy rotation look broken.

So the rotation procedure is:

1. `wrangler secret put SERVER_KEY` (this alone deploys the new version).
2. **Evict the resident isolate**: stop the connector on every machine (so the WebSocket drops and the DO can go idle), and let a minute pass — or force eviction by redeploying the same code (`wrangler deploy` again), which is also the recovery move for any sick isolate.
3. *Then* verify: open `/setup?token=<new SETUP_TOKEN>` (if you rotated that too), re-enter the Feishu credentials, and pair a connector — the new `SERVER_KEY` signs the new token.

The same pinning applies after ordinary code deploys: a resident isolate runs the old code until it goes idle or is evicted. If a freshly deployed fix "doesn't seem to be live", evict first, conclude second.

## Updating your deployment

- One-click deploys: push (or sync from upstream) to your copy's `main` — Workers Builds redeploys automatically.
- Manual: `git pull` in your clone, then `wrangler deploy`. Database migrations inside the Durable Object run automatically on first use after the deploy; no manual step exists or is needed.
- After any update, remember the resident-isolate rule above when verifying new behavior.

## Troubleshooting

- **Setup page / any page unreachable from mainland China on `*.workers.dev`** — expected; bind a [custom domain](#custom-domain).
- **Webhook switch fails with a URL-verification error** — Feishu's servers cannot reach your host. On `workers.dev`: mandatory custom domain. On a custom domain: mainland reachability of Cloudflare-fronted domains varies; try another domain, then run the switch again from the setup page.
- **Published the app, but the verifying DM never arrives** — config and publish can land out of order; the setup page offers "re-run the switch" for exactly this. Re-publish, re-run, DM again.
- **Every steward request returns 1101 while plain Worker routes still answer** — a Cloudflare DO/platform incident (seen in the spike, §5): redeploying does not help; the connector's retry loop self-heals and no persisted data is lost. Wait it out.
- **Connector reconnect-loops from a mainland machine** — same blocked-`workers.dev` cause; point it at the custom domain.
- **A just-rotated secret "doesn't work"** — resident isolate; see [secrets and rotation](#secrets-and-rotation).
